## 1. Tujuan

Mengatur tampilan dan perilaku UI terkait autentikasi dan hak akses. Aturan otorisasi sebenarnya ada di `docs/backend/06.RBAC.md` dan `04.SECURITY.md`.

---

## 2. Prinsip

- **UI hanya mencerminkan izin; server yang menegakkannya.** Menyembunyikan tombol/menu bukan keamanan.
- Izin efektif = `role` + `PenugasanStruktural` aktif + `PeriodeKhidmat` aktif.
- Proxy (`proxy.ts`) melindungi rute; Server Action memeriksa ulang secara mandiri.
- PW/PC tidak pernah melihat data organisasi lain.
- 15 role bersifat final — jangan hardcode daftar role di komponen; gunakan enum/helper permissions (`modules/authentication/domain/permissions.ts`) `[ISI: konfirmasi API helper]`.

---

## 3. Alur Login & Sesi

| Langkah | Perilaku |
| :--- | :--- |
| Akses rute terlindungi tanpa sesi | Proxy redirect ke `/login?callbackUrl=<rute>` |
| Submit login | `authClient.signIn.email({ email, password })` |
| Sukses | `router.push(callbackUrl ?? '/dashboard')` lalu `router.refresh()` |
| Gagal | Pesan di form (`role="alert"`), tanpa membedakan "email tidak ada" vs "password salah" |
| Logout | `authClient.signOut()` lalu arahkan ke `/login` |
| Sesi habis | Toast + redirect ke `/login` dengan `callbackUrl` |

Spesifikasi halaman login:
- Layout: `[ISI: split screen / kartu tengah]`
- Teks: "Platform Digital Lembaga Ittihadul Muballighin"
- Field: email, password (tombol tampil/sembunyi), "Lupa password" `[ISI]`
- Rate limit login 10 req/menit/IP → tampilkan pesan "Terlalu banyak percobaan" pada 429.
- Login Google (OAuth): `[ISI: ada/tidak di MVP]`

Catatan: contoh halaman login di `AUTH_SETUP.md` hanya untuk uji dan memakai warna Tailwind mentah — ganti dengan token design system.

Sesi: server memakai `getSession()` (`@/lib/auth`); client memakai `useSession()`/`authClient.getSession()` dari auth client. Hindari fetch sesi ganda di halaman yang sama.

## 4. MFA

Wajib untuk: `OWNER`, `ADMIN_SEKRETARIAT`, `ADMIN_BIDANG_SAFARI`, `ADMIN_BIDANG_PESANTREN_RAMADAN`.

- Jika `twoFactorEnabled` belum aktif, proxy mengarahkan ke `/dashboard/security/mfa`; halaman lain di-block.
- Halaman MFA: `[ISI: langkah QR TOTP → verifikasi kode → kode cadangan]`
- Banner pengingat bagi role wajib MFA yang belum aktif: `[ISI]`
- Login role wajib MFA: tampilkan layar input kode setelah password benar `[ISI]`

## 5. UI Berbasis Role

| Elemen | Aturan |
| :--- | :--- |
| Sidebar | Dibangun dari izin role; item tanpa izin disembunyikan |
| Tombol aksi (buat/ubah/hapus/approve) | Tampil hanya bila role punya izin pada modul tersebut |
| Aksi tidak tersedia karena status | Disabled + tooltip alasan (mis. "Surat sudah SENT") |
| Halaman | Tetap tangani kasus pengguna masuk lewat URL langsung (server menolak) |
| Dashboard `/dashboard` | Konten berbeda per kelompok role `[ISI]` |

Legenda RBAC → perilaku UI:

| Simbol RBAC | Arti | Perilaku UI |
| :--- | :--- | :--- |
| ✅ | Full | Semua aksi tersedia |
| 🔶 | Limited | Lihat + ubah, tanpa tombol hapus |
| 🔍 | Read only | Hanya lihat, tanpa tombol aksi |
| ➕ | Create only | Hanya tombol buat |
| ✏️ | Update own | Hanya ubah data milik sendiri |
| ❌ | Tidak ada akses | Menu & halaman tidak ditampilkan |
| 🌍 / 🏢 / 👤 | Scope global / organisasi / personal | Tampilkan `ScopeIndicator` bila bukan global |

## 6. Akun Organisasi & Scope

- Akun `ORGANIZATIONAL` memakai satu akun bersama per organisasi; semua form mutasi menyertakan `namaPengisi` dan `jabatanPengisi`.
- Topbar menampilkan organisasi yang aktif (mis. "PC Surabaya") agar pengguna sadar scope datanya.
- Tidak ada kontrol pindah-organisasi untuk PW/PC. Jika data organisasi lain diminta lewat URL → tampilkan 404 (jangan konfirmasi keberadaannya).
- `PONDOK_INTERNAL` memiliki sub-kategori (Induk, Unit, Cabang, MHM, Ma'had Aly) dari `UnitOrganisasi.subKategori` — tampilkan sebagai label, bukan sebagai role.

## 7. Alur LEMBAGA_EKSTERNAL

| Tahap | UI |
| :--- | :--- |
| Belum punya akun | Form publik `/permohonan-guru-bantu` (tanpa login) |
| Setelah submit | Halaman konfirmasi + nomor/kode pelacakan `[ISI]` |
| Status `DIAJUKAN` | Tidak ada login |
| Disetujui | Akun dibuat otomatis; kirim info login `[ISI: manual di MVP — tanpa auto notif WA/Email]` |
| Setelah login | Lihat status permohonan, input laporan mingguan WK, umpan balik |

## 8. Penanganan 401 / 403

| Kondisi | Perilaku |
| :--- | :--- |
| 401 / `Unauthorized` | Redirect ke `/login?callbackUrl=...` |
| 403 / `Forbidden` | Halaman/alert "Anda tidak memiliki akses" + tautan ke `/dashboard` |
| Redirect proxy `?error=unauthorized` | `/dashboard` menampilkan toast akses ditolak sekali, lalu bersihkan query |
| 404 untuk data di luar scope | Tampilkan not-found umum |
| 429 | "Terlalu banyak permintaan, coba lagi sebentar" |

Percobaan akses yang ditolak dicatat server di `AuditLog` (`ACCESS_DENIED`) — UI tidak perlu melaporkannya.

## 9. Larangan Keras

- ❌ DILARANG menganggap menyembunyikan UI sebagai otorisasi.
- ❌ DILARANG hardcode daftar role di komponen.
- ❌ DILARANG menampilkan data organisasi lain untuk PW/PC.
- ❌ DILARANG menyimpan token/sesi di `localStorage`.
- ❌ DILARANG membedakan pesan "email tidak terdaftar" dan "password salah".
- ❌ DILARANG form organisasi tanpa `namaPengisi` dan `jabatanPengisi`.
- ❌ DILARANG membiarkan role wajib MFA menjelajah dashboard tanpa MFA aktif.
