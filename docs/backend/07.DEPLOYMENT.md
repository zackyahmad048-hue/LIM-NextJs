## 1. Tujuan

Dokumen ini mendefinisikan strategi deployment, pipeline CI/CD, dan manajemen environment untuk Platform LIM. Tujuannya adalah memastikan proses rilis yang aman, cepat, dan dapat dipulihkan (recoverable) kapan pun diperlukan.

## 4. CI/CD Pipeline

### 4.1 Trigger
Pipeline dijalankan otomatis pada:
- Setiap push ke branch `main`, `staging`, atau PR
- Setiap PR yang dibuat atau di-update

### 4.2 Pipeline Steps

CI aktual ada di `.github/workflows/ci.yml` (job `quality`, Bun, Prisma 6):

```yaml
name: CI

on:
  push:
    branches: [main, staging]
  pull_request:
    branches: [main, staging]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: latest
      - run: bun install --frozen-lockfile
      - run: bunx prisma@6 generate
      - run: bun run lint
      - run: bun run typecheck
      - run: bun run test
      - name: API spec drift check
        run: bun run api:spec && git diff --exit-code -- openapi docs/api
```

Catatan: E2E Playwright (`bun run test:e2e`) dan build produksi belum menjadi langkah wajib di workflow ini; jalankan terpisah sesuai kebutuhan rilis.

### 4.3 Deployment Steps

- Preview: Otomatis oleh Vercel saat PR dibuat.
- Staging: Merge ke branch `staging` → Vercel auto-deploy.
- Production: Merge ke branch `main` → Vercel auto-deploy.

### 5. Database Migration Strategy
### 5.1 Development

Gunakan `db push` untuk iterasi cepat (tanpa file migration):

```bash
bunx prisma@6 db push
```
### 5.2 Production

WAJIB menggunakan `migrate deploy` dengan file migration yang sudah di-commit:

```bash
# 1. Buat migration file
bunx prisma@6 migrate dev --name <nama-migration>

# 2. Commit file migration ke Git
git add prisma/migrations/
git commit -m "chore(db): add migration <nama>"

# 3. Deploy ke production
bunx prisma@6 migrate deploy
```

### 5.3 Baseline Database yang Sudah Disinkron via `db push`

Jika database (dev/staging/production) sudah memiliki skema yang sesuai tetapi riwayat `_prisma_migrations` belum mencatat migration yang ada di repo (mis. `0_init`), **jangan** menjalankan `migrate deploy` langsung.

1. Pastikan `DATABASE_URL` menunjuk ke database target yang benar (backup/snapshot bila perlu).
2. Tandai migration sebagai sudah diterapkan:
   ```bash
   bunx prisma@6 migrate resolve --applied 0_init
   ```
3. Verifikasi: `bunx prisma@6 migrate status`
4. Baru jalankan `bunx prisma@6 migrate deploy` untuk migration berikutnya.

> Jalankan hanya pada database yang skemanya memang sudah sesuai dengan migration tersebut. Salah target = riwayat migrasi korup.

### 5.3.1 `bun run build` menjalankan `generate` + `migrate deploy`

`package.json` → `"build": "prisma generate && prisma migrate deploy && next build"`. Vercel memakai `build` apa adanya, jadi:

- `prisma generate` mencetak Prisma Client untuk platform build (Vercel = `rhel-openssl-3.0.x`). Tanpa ini, engine yang ter-commit (`debian-openssl-3.0.x`) tidak dikenali dan build gagal dengan `PrismaClientInitializationError: could not locate the Query Engine`.
- `prisma migrate deploy` menyelaraskan skema pada `DATABASE_URL` environment tersebut sebelum Next.js mem-prerender halaman yang query DB. Efek samping: `DATABASE_URL` yang salah target akan dibuatkan skema lengkap di DB itu — cek host DB yang dicetak `migrate deploy` di log build.

### 5.4 Aturan Migration

- **DILARANG** mengubah migration yang sudah di-deploy ke production.
- **DILARANG** drop table/column tanpa backup data.
- Migration yang destruktif WAJIB melalui review minimal 2 developer.
- Setiap migration WAJIB memiliki rollback plan.

### 6. Environment Variables

### 6.1 Kategori Variables

| a                  | Akses                | Contoh                                                      |
| ------------------ | -------------------- | ----------------------------------------------------------- |
| `NEXT_PUBLIC_*` | Client & Server      | `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_GA_ID`              |
| Tanpa prefix       | HANYA Server | `DATABASE_URL`, `BETTER_AUTH_SECRET`, `R2_ACCESS_KEY` |

### 6.2 Variables Wajib per Environment

```env
# === WAJIB (semua environment) ===
DATABASE_URL="postgresql://..."
BETTER_AUTH_SECRET="..."          # min 32 chars, random
BETTER_AUTH_URL="https://..."     # sesuai origin environment
BETTER_AUTH_ALLOWED_HOSTS=""      # opsional, host tambahan dipisah koma; host Vercel (VERCEL_URL/VERCEL_BRANCH_URL) otomatis diizinkan
NEXT_PUBLIC_APP_URL="https://..."

# === API v1 (wajib untuk /api/v1 di production) ===
API_ALLOWED_ORIGINS="https://app.example.com,https://admin.example.com"  # allowlist CORS (tanpa wildcard untuk kredensial)
UPSTASH_REDIS_REST_URL="https://..."
UPSTASH_REDIS_REST_TOKEN="..."    # rate limit + idempotency (Upstash Redis); tanpa ini, perilaku proteksi di prod terdegradasi/gagal sesuai implementasi

# === STORAGE S3-compatible (wajib jika fitur upload/presign dipakai) ===
# Dipakai oleh POST /api/v1/uploads/presign (Cloudflare R2 atau Supabase Storage S3 endpoint)
R2_ACCOUNT_ID=""                  # R2: opsional jika R2_ENDPOINT diisi; non-R2 bisa kosong
R2_ACCESS_KEY_ID="..."
R2_SECRET_ACCESS_KEY="..."
R2_BUCKET_NAME="..."
R2_ENDPOINT="..."                 # contoh R2: https://<accountid>.r2.cloudflarestorage.com ; Supabase: https://<project>.storage.supabase.co/storage/v1/s3
R2_REGION=""                      # R2: auto; Supabase: region project
# R2_FORCE_PATH_STYLE=true        # opsional; otomatis true untuk endpoint non-R2

# === EMAIL (opsional, sesuai fitur) ===
RESEND_API_KEY="..."
```

Referensi lengkap: `.env.example`. Endpoint realtime (`/api/realtime`) membutuhkan `NEON_REALTIME_URL`/`NEON_REALTIME_SECRET` jika digunakan.

### 6.3 Aturan Secrets

- DILARANG commit `.env*` ke Git (sudah ada di `.gitignore`).
- DILARANG log environment variable (`console.log(process.env.DATABASE_URL)`).
- Gunakan **Vercel Environment Variables** untuk production/staging.
- Gunakan **Neon Branching** untuk development database.

### 7. Release Process

### 7.1 Semantic Versioning

Format: `MAJOR.MINOR.PATCH`

- **MAJOR**: Perubahan breaking (misal: ubah schema database)
- **MINOR**: Fitur baru (backward compatible)
- **PATCH**: Bug fix

### 7.2 Release Checklist

- Semua test lolos (unit, integration, E2E)
- Lighthouse score > 90
- Tidak ada TypeScript error
- Migration sudah di-review
- Changelog sudah di-update
- Backup database sudah dilakukan

### 7.3 Changelog Format

```markdown
## [1.2.0] - 2026-11-15
### Added
- Fitur penomoran surat dinamis
- Role ADMIN_BIDANG_SAFARI

### Fixed
- Bug cross-check laporan mingguan

### Changed
- Update schema Prisma untuk mendukung sub-tipe pondok
```

### 8. Rollback Strategy

### 8.1 Application Rollback

Vercel otomatis menyimpan deployment history. Rollback via:

- Vercel Dashboard → Promote previous deployment
- Atau: v`ercel rollback`

### 8.2 Database Rollback

- ***Jika ada migration destruktif**: Restore dari backup Neon.
- **Jika data corrupt**: Restore point-in-time (Neon support).
- **Target RTO (Recovery Time Objective)**: < 1 jam
- **Target RPO (Recovery Point Objective)**: < 5 menit

## 9. Monitoring & Observability

### 9.1 Application Monitoring

- **Vercel Analytics**: Web Vitals, page speed
- **Sentry**: Error tracking & performance monitoring
- **PostHog**: User behavior analytics

### 9.2 Database Monitoring

- **Neon Dashboard**: Query performance, connection count
- **Prisma Studio**: Inspect data lokal
- **Slow Query Alert**: Query > 1 detik akan di-log

### 9.3 Alerting

| Alert                 | Threshold  | Action             |
| --------------------- | ---------- | ------------------ |
| Error Rate            | \> 1%      | Slack notification |
| Response Time         | \> 2s      | Investigate        |
| Database Connections  | \> 80%     | Scale Neon         |
| Failed Login Attempts | \> 5/menit | Block IP           |

## 10. Backup & Recovery

### 10.1 Backup Schedule

- **Hourly**: Automatic by Neon (point-in-time recovery)
- **Daily**: Export ke Cloudflare R2
- **Weekly**: Full backup ke cold storage

### 10.2 Recovery Test

- **Frekuensi**: Setiap 3 bulan
- **Metode**: Restore backup ke environment staging, verifikasi data integrity
- **PIC**: `OWNER` + `ADMIN_SEKRETARIAT`

## 11. Larangan Keras

- ❌ DILARANG deploy langsung ke production tanpa melalui staging.
- ❌ DILARANG mengubah environment variable production tanpa review.
- ❌ DILARANG drop database production tanpa backup.
- ❌ DILARANG commit .env atau secret ke Git.
- ❌ DILARANG skip CI pipeline untuk merge ke main.
- ❌ DILARANG deploy di hari Jumat sore atau weekend (kecuali emergency).
- ❌ DILARANG menggunakan database production untuk testing manual.
