## 1. Tujuan

Dokumen ini mendefinisikan standar workflow pengembangan, konvensi kode, dan proses code review untuk Platform LIM. Tujuannya adalah memastikan konsistensi kualitas kode dan kolaborasi tim yang efektif.

## 2. Local Environment Setup

### 2.1 Prerequisites
- **Node.js**: v20.9+ (LTS)
- **Bun**: v1.1+ (package manager & runtime)
- **Git**: v2.40+
- **VS Code** / **Cursor** (recommended)

### 2.2 Initial Setup
```bash
# 1. Clone repository
git clone <repo-url>
cd lim-platform

# 2. Install dependencies
bun install

# 3. Setup environment variables
cp .env.example .env.local
# Edit .env.local dengan credentials lokal

# 4. Setup database
bunx prisma@6 generate
bunx prisma@6 db push
bun run db:seed  # Seed data awal

# 5. Jalankan dev server
bun run dev
```

### 2.3 Perintah Pengembangan Harian

```bash
bun run dev              # Start dev server (Turbopack)
bun run lint             # Check linting
bun run typecheck        # Check TypeScript errors
bun run format           # Format kode dengan Prettier
bun run test             # Jalankan unit test
bun run test:watch       # Watch mode untuk test
bunx prisma@6 studio     # Buka UI database visual
```

## 3. Git Workflow

### 3.1 Alur Kerja Standar
```
1. Pull latest dari main
   ↓
2. Buat branch baru (feat/xxx atau fix/xxx)
   ↓
3. Kerjakan fitur/fix
   ↓
4. Commit dengan Conventional Commits
   ↓
5. Push & buat Pull Request
   ↓
6. Code Review (minimal 1 reviewer)
   ↓
7. CI Pipeline lolos
   ↓
8. Merge ke main (squash merge)
```

### 3.2 Aturan Branch

- **DILARANG** push langsung ke `main` atau `staging`.
- **WAJIB** buat PR untuk setiap perubahan.
- **WAJIB** resolve semua comment reviewer sebelum merge.
- **WAJIB** squash merge untuk menjaga history tetap bersih.

## 4. Branching Strategy

### 4.1 Tipe Branch

| Prefix        | Kegunaan                      | Contoh                    |
| ------------- | ----------------------------- | ------------------------- |
| `feat/`     | Fitur baru                    | `feat/letter-numbering` |
| `fix/`      | Bug fix                       | `fix/wk-cross-check`    |
| `refactor/` | Refactoring (bukan fitur/fix) | `refactor/auth-module`  |
| `docs`     | Dokumentasi                   | `docs/rbac-matrix`      |
| `chore/`    | Maintenance, config, deps     | `chore/upgrade-prisma`  |
| `test/`     | Test saja                     | `test/letter-numbering` |
| `hotfix/`   | Fix urgent di production      | `hotfix/auth-bypass`    |

### 4.2 Naming Convention

- Gunakan lowercase dan hyphen: feat/safari-jurnal-harian
- Maksimal 50 karakter
- Harus deskriptif tapi ringkas

## 5. Commit Convention

### 5.1 Format (Conventional Commits)

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### 5.2 Tipe Commit

| Type         | Kegunaan                            |
| ------------ | ----------------------------------- |
| `feat`     | Fitur baru                          |
| `fix`      | Bug fix                             |
| `docs`     | Dokumentasi                         |
| `style`    | Formatting, missing semicolons, dll |
| `refactor` | Refactoring kode                    |
| `perf`     | Performance improvement             |
| `test`     | Menambah/mengedit test              |
| `chore`    | Maintenance, build, CI              |
| `ci`       | Perubahan CI/CD config              |
| `revert`   | Revert commit sebelumnya            |

### 5.3 Scope

Scope adalah modul/domain yang diubah:

- `auth`, `letter`, `wk` (wajib khidmah), `safari`, `pesantren`, `falak`, `cms`, `dakwah`, `binaan`, `db` (database), `ui`

### 5.4 Contoh Commit

```bash
feat(letter): implementasi penomoran surat dinamis

- Tambah tabel LetterNumberCounter
- Implementasi transaction untuk race condition
- Tambah unit test untuk format nomor

Closes #42
```

```bash
fix(wk): perbaiki cross-check laporan mingguan

Bug: Laporan guru dan lembaga tidak ter-compare dengan benar
karena field periodeMinggu berbeda tipe data.

Fix: Cast kedua field ke Int sebelum compare.

Fixes #123
```

## 6. Code Review Guidelines

### 6.1 Checklist Reviewer

- Kode mengikuti standar coding (lihat section 7)
- Tidak ada `any` type
- Validasi Zod di setiap Server Action
- Otorisasi dicek di Server Action (bukan hanya UI)
- Test sudah ditulis untuk logic kritis
- Dokumentasi di-update jika perlu
- Tidak ada `console.log` yang tertinggal

### 6.2 Aturan Review

- Reviewer WAJIB memberikan feedback konstruktif.
- Author WAJIB merespon semua comment (resolve atau diskusi).
- Review maksimal 24 jam setelah PR dibuat.
- Jika ada disagreement, diskusikan di meeting, bukan di PR.

### 6.3 Label PR

| Label                | Arti                            |
| -------------------- | ------------------------------- |
| `ready-for-review` | Siap di-review                  |
| `needs-changes`    | Perlu perubahan                 |
| `approved`         | Disetujui, bisa merge           |
| `blocked`          | Terhalang dependency            |
| `wip`              | Work in progress, jangan review |

## 7. Coding Standards
### 7.1 TypeScript

- WAJIB Strict Mode (tidak ada `any`).
- Gunakan `interface` untuk object shape, `type` untuk union/intersection.
- Naming:
    - `PascalCase` untuk Component, Type, Interface, Enum
    - `camelCase` untuk function, variable, field
    - `UPPER_SNAKE_CASE` untuk constant, enum value

## 7.2 React / Next.js

- Server Components by default.
- Tambahkan `'use client'` HANYA jika memang butuh interaktivitas browser.
- JANGAN tulis `useMemo`, `useCallback`, `memo()` manual (React Compiler aktif).
- Gunakan `Suspense` untuk loading state.

## 7.3 Server Actions

- **WAJIB** validasi input dengan Zod.
- **WAJIB** cek otorisasi di dalam action.
- Return format `ActionResult<T>` yang konsisten.
- Panggil `revalidatePath()` atau `revalidateTag()` setelah mutasi.

## 7.4 Error Handling

```typescript
// ✅ BENAR
try {
  const result = await someAction()
  return { success: true, data: result }
} catch (error) {
  console.error('[ActionName]', error)
  return { success: false, error: 'Terjadi kesalahan' }
}

// ❌ SALAH
try {
  // ...
} catch (error) {
  // Jangan biarkan error silent
}
```

## 9. Testing Requirements
### 9.1 Test Wajib

- **Unit Test**: Untuk semua logic di `domain/` dan `application/`.
- **Integration Test**: Untuk Server Actions kritis.
- **E2E Test**: Untuk user journey utama (login, submit surat, input laporan).

### 9.2 Coverage Target

| Layer               | Target |
| ------------------- | ------ |
| `domain/`         | 90%+   |
| `application/`    | 80%+   |
| `infrastructure/` | 70%+   |
| `presentation/`   | 60%+   |

### 9.3 Menjalankan Test

```bash
bun run test              # Semua test
bun run test:watch        # Watch mode
bun run test:coverage     # Dengan coverage report
bun run test:e2e          # Playwright E2E
```

## 10. Larangan Keras

- ❌ DILARANG push langsung ke main atau staging.
- ❌ DILARANG merge PR tanpa review.
- ❌ DILARANG skip CI pipeline.
- ❌ DILARANG commit .env atau secret ke Git.
- ❌ DILARANG menggunakan any type.
- ❌ DILARANG menulis useMemo/useCallback manual.
- ❌ DILARANG bypass validasi Zod di Server Actions.
- ❌ DILARANG meninggalkan console.log di production code.
- ❌ DILARANG membuat PR raksasa (> 500 lines). Pecah jadi PR kecil.
- ❌ DILARANG merge PR dengan konflik unresolved.
