## 1. Tujuan

Architecture Decision Records (ADR) adalah log singkat yang mendokumentasikan **keputusan arsitektur penting**, **konteks di baliknya**, dan **konsekuensinya**. 

Tujuan ADR:
- Agar developer baru bisa memahami **MENGAPA** sistem dirancang seperti ini.
- Agar keputusan tidak hilang saat ada pergantian developer.
- Agar keputusan yang sama tidak diperdebatkan berulang kali.
- Agar perubahan arsitektur dapat di-track dan di-review.

---

## 2. Cara Menggunakan ADR

### 2.1 Kapan Membuat ADR?
Buat ADR baru ketika:
- Memilih teknologi baru (framework, library, database).
- Mengubah pola arsitektur (misal: dari MVC ke DDD).
- Mengubah aturan bisnis fundamental (misal: model akun).
- Ada keputusan yang akan berdampak jangka panjang.

### 2.2 Kapan TIDAK Perlu ADR?
- Perubahan kecil (typo, styling, refactor minor).
- Bug fix rutin.
- Penambahan fitur yang tidak mengubah arsitektur.

### 2.3 Status ADR
| Status | Arti |
|--------|------|
| `Proposed` | Masih dalam pembahasan |
| `Accepted` | Sudah disetujui dan diimplementasikan |
| `Deprecated` | Sudah tidak dipakai, tapi masih ada untuk referensi |
| `Superseded` | Digantikan oleh ADR baru (sebutkan ADR penggantinya) |

## 5. Contoh ADR

### ADR-001: Pemilihan Next.js 16 dan Turbopack
```
Status: Accepted
Tanggal: 2026-11-14
Deklaran: Tim Arsitektur LIM
```

**Konteks**

Platform LIM membutuhkan framework modern yang mendukung:

- Server-side rendering untuk SEO (portal publik).
- Server Components untuk performa optimal.
- Server Actions untuk mutasi data tanpa REST API.
- Developer experience yang baik untuk tim kecil.

**Keputusan**
Kami memutuskan menggunakan **Next.js 16** dengan **Turbopack** sebagai default bundler.

**Alternatif yang Dipertimbangkan**

**Opsi A: Remix**

- Kelebihan: Web standards, loader/action pattern yang bersih.
- Kekurangan: Ekosistem lebih kecil, tidak ada native Server Actions.

**Opsi B: Nuxt (Vue)**

- Kelebihan: DX bagus, ekosistem mature.
- Kekurangan: Tim lebih familiar dengan React, harus belajar Vue.

**Opsi C: Next.js 14/15 (versi lama)**

- Kelebihan: Lebih stabil, dokumentasi lebih banyak.
- Kekurangan: Tidak ada React Compiler, Turbopack belum default.

**Konsekuensi**

**Positif:**

- Build time 5-10x lebih cepat dengan Turbopack.
- Auto-memoization dengan React Compiler.
- Server Actions mengurangi boilerplate API.
- Cache Components untuk performa optimal.

**Negatif / Risiko:**

- Next.js 16 relatif baru, beberapa library mungkin belum kompatibel.
- Breaking changes pada async `params`/`searchParams` perlu adaptasi.

**Dampak ke Modul Lain:**

- Semua modul harus mengikuti App Router pattern.
- Tidak boleh pakai `pages/` directory.
- Semua mutasi data via Server Actions.

## ADR-002: Pemilihan Better Auth
```
Status: Accepted
Tanggal: 2026-11-14
Deklaran: Tim Arsitektur LIM
```

**Konteks**

Platform LIM membutuhkan sistem autentikasi yang mendukung:

- Personal account (1 orang = 1 akun).
- **Organizational account** (1 organisasi = 1 akun bersama) — ini adalah requirement unik dari PKO LIM.
- Role-based access control (RBAC) yang granular.
- Multi-factor authentication (MFA) untuk role kritis.

**Keputusan**

Kami memutuskan menggunakan **Better Auth** dengan Prisma Adapter.

**Alternatif yang Dipertimbangkan**

**Opsi A: NextAuth (Auth.js)**

- Kelebihan: Populer, dokumentasi banyak.
- Kekurangan: Tidak ada native support untuk organizational accounts. Perlu custom logic yang kompleks.

**Opsi B: Clerk**

- Kelebihan: DX sangat bagus, UI components siap pakai.
- Kekurangan: Mahal untuk skala besar, vendor lock-in, tidak bisa self-host.

**Opsi C: Custom Auth**

- Kelebihan: Kontrol penuh.
- Kekurangan: Butuh waktu lama, rawan bug keamanan.

**Konsekuensi**

**Positif:**

- Native support untuk organizational accounts.
- Database-agnostic (bisa ganti DB tanpa ganti auth).
- Type-safe, terintegrasi baik dengan TypeScript.
- Bisa self-host, tidak ada vendor lock-in.

**Negatif / Risiko:**

- Library relatif baru, komunitas lebih kecil dari NextAuth.
- Perlu setup manual untuk beberapa fitur advanced.

### ADR-003: Model Akun Organizational

- **Status**: Accepted
- **Tanggal**: 2026-11-14
- **Deklaran**: Tim Arsitektur LIM

**Konteks**

Berdasarkan PKO MUNAS II, organisasi LIM memiliki struktur hierarki:

- Pengurus Pusat (PP)
- Pengurus Wilayah (PW) — tingkat provinsi
- Pengurus Cabang (PC) — tingkat kabupaten/kota
- Pondok/Madrasah Internal

Setiap unit organisasi bisa memiliki banyak pengurus yang bergantian mengelola akun. Ini berbeda dengan akun personal (1 orang = 1 akun).

**Keputusan**

Kami menerapkan **dua jenis akun:**

- **Personal Account**: Untuk individu (Owner, Guru Bantu, Dosen, dll).
- **Organizational Account**: Untuk organisasi (PW, PC, Pondok).

Organizational Account memiliki field tambahan:

- `namaPengisi` — siapa yang sedang mengisi form saat ini.
- `jabatanPengisi` — jabatan pengisi saat ini.

Field ini WAJIB diisi setiap kali ada mutasi data dari akun organizational, untuk audit trail.

**Alternatif yang Dipertimbangkan**

**Opsi A: Satu akun per orang, dengan relasi ke organisasi**

- Kelebihan: Audit trail lebih jelas.
- Kekurangan: Tidak sesuai dengan realita operasional (1 akun dipakai bersama).

**Opsi B: Multi-user per organisasi (seperti Google Workspace)**

- Kelebihan: Setiap orang punya akun sendiri.
- Kekurangan: Ribet untuk organisasi kecil (PC/PAC), butuh manajemen user tambahan.

**Konsekuensi**

**Positif:**

- Sesuai dengan cara kerja organisasi LIM di lapangan.
- Mudah diadopsi oleh pengguna.
- Audit trail tetap terjaga lewat field `namaPengisi`/`jabatanPengisi`.

**Negatif / Risiko:**

- Risiko keamanan jika password akun bersama bocor.
- Perlu MFA untuk akun organisasi kritis.
- Perlu edukasi user bahwa mereka WAJIB mengisi nama pengisi.

### ADR-008: Penyederhanaan Role dari 21 menjadi 15

- **Status**: Accepted
- **Tanggal**: 2026-11-15
- **Deklaran**: Tim Arsitektur LIM

**Konteks**

Awalnya sistem dirancang dengan 21 role terpisah, termasuk:

- `PONDOK_INDUK`, `PONDOK_UNIT`, `PONDOK_CABANG_NON_ZONASI`, `PONDOK_CABANG_ZONASI`, `MHM`, `MAHAD_ALY` (6 role terpisah untuk pondok).
- `LEMBAGA_EKSTERNAL` dan `LEMBAGA_EKSTERNAL_PEMOHON` (2 role untuk lembaga).
- `DOSEN` sebagai role terpisah.

Hal ini menyebabkan:

- Matriks RBAC menjadi sangat kompleks (21 kolom × 10 modul).
- Maintenance sulit saat ada perubahan struktur organisasi.
- Banyak role yang sebenarnya memiliki hak akses serupa.

**Keputusan**

Kami menyederhanakan menjadi 15 role:

- Digabung: Semua `PONDOK_*` menjadi `PONDOK_INTERNAL`. Sub-tipe disimpan di tabel `UnitOrganisasi` sebagai field `subKategori`.
- Digabung: `LEMBAGA_EKSTERNAL_PEMOHON` ke `LEMBAGA_EKSTERNAL`. Flow permohonan via form publik, akun dibuat otomatis setelah disetujui.
- Dihapus: `DOSEN` karena data masuk via file Excel, bukan input langsung ke sistem.

**Alternatif yang Dipertimbangkan**

**Opsi A: Tetap 21 role**

- Kelebihan: Sangat granular.
- Kekurangan: Kompleks, sulit di-maintain, RBAC matrix terlalu besar.

**Opsi B: Lebih ekstrem, jadi 10 role**

- Kelebihan: Sangat sederhana.
- Kekurangan: Kehilangan granularitas yang dibutuhkan untuk beberapa modul.

**Konsekuensi**

**Positif:**

- RBAC matrix lebih mudah dipahami dan diimplementasikan.
- Sub-tipe pondok tetap bisa dilacak via `subKategori` di database.
- Flow lembaga eksternal lebih natural (form publik → auto-create akun).

**Negatif / Risiko:**

- Perlu dokumentasi yang jelas tentang sub-tipe PONDOK_INTERNAL.
- Tim perlu memahami bahwa "role" dan "sub-tipe organisasi" adalah dua konsep berbeda.

**Dampak ke Modul Lain:**

- Schema Prisma: Enum Role disederhanakan.
- Tabel UnitOrganisasi: Perlu field subKategori (enum terpisah).
- Modul Permohonan Guru Bantu: Flow auto-create akun setelah approve.

### ADR-009: Cache publik dengan `'use cache'` (Cache Components)

```
Status: Accepted
Tanggal: 2026-11-19
Deklarasi: Tim Arsitektur LIM
```

**Konteks**

Halaman publik `/artikel` dan beranda membaca tabel `Article` pada setiap permintaan, padahal isinya jarang berubah dan sama untuk semua pengunjung.

**Keputusan**

Kueri publik artikel (`listPublishedArticles`, `getPublishedArticleBySlug`) dibungkus `'use cache'` dengan `cacheLife('hours')` dan `cacheTag('articles')`. Setiap mutasi CMS (`create-article`, `publish-article`) memanggil `updateTag('articles')`.

**Alternatif yang Dipertimbangkan**

**Opsi A: Tanpa cache**
- Kelebihan: selalu segar, tidak ada logika invalidasi.
- Kekurangan: setiap pengunjung membebani database; tidak memanfaatkan Cache Components.

**Opsi B: `revalidatePath` saja**
- Kelebihan: sederhana.
- Kekurangan: tidak membagikan hasil antar pengunjung dengan cache key yang sama, dan tidak mencakup halaman detail per-slug.

**Konsekuensi**

**Positif:** halaman publik artikel menjadi static shell yang dilayani cepat; data tetap segar di bawah satu jam walaupun ada mutasi yang lupa meng-invalidasi.

**Negatif / Risiko:** semua jalur mutasi artikel WAJIB memanggil `updateTag('articles')`. Jalur baru (edit/delete/unpublish) harus menambahkannya.

### ADR-010: Tenancy Isolation via `unitId` + PostgreSQL RLS

```
Status: Proposed
Tanggal: 2026-11-23
Deklarasi: Tim Arsitektur LIM
```

**Konteks**

Platform LIM memiliki 15 role, akun PERSONAL dan ORGANIZATIONAL (PW/PC/Pondok/Lembaga), dan 11 domain bisnis. Isolasi data saat ini mengandalkan filter relasi di application layer (docs `02.PRISMA_SCHEMA.md` §12). Pendekatan ini rapuh: query baru mudah lupa scope, join relasi mahal, dan tidak ada defense-in-depth di level database.

**Keputusan**

Adopsi **multi-tenancy berbasis `unitId` + PostgreSQL Row-Level Security (RLS)**:

1. Tambah `UnitOrganisasi.parentId` untuk hierarki.
2. Tambah `unitId` pada aggregate root tenant-scoped (nullable di F1, backfill+enforce di F2).
3. Runtime app memakai role DB `lim_app` (NOSUPERUSER, NOBYPASSRLS) via `DATABASE_URL` pooled; migration memakai owner via `DIRECT_URL`.
4. Setiap query tenant-scoped berjalan dalam `withTenant(...)` yang membuka transaksi dan `SET LOCAL app.scope/app.unit_id/app.user_id`.
5. Tabel tenant-scoped mendapat policy RLS (`USING`/`WITH CHECK`) dan `FORCE ROW LEVEL SECURITY`.
6. Prisma `$extends` guard menolak query tenant-scoped tanpa tenant context (F3).

Desain detail: `docs/backend/10.BACKEND_SYSTEM_DESIGN.md`.

**Alternatif yang Dipertimbangkan**

**Opsi A: Filter relasi di application layer (status quo)**
- Kelebihan: nol migration, sederhana.
- Kekurangan: mudah bocor, tidak ada DB-level guard, query kompleks.

**Opsi B: `unitId` di app layer tanpa RLS**
- Kelebihan: lebih murah dari RLS, query lebih sederhana.
- Kekurangan: satu query lupa filter = bocor data; tidak defense-in-depth.

**Opsi C: Schema-per-tenant**
- Kelebihan: isolasi kuat.
- Kekurangan: kompleksitas operasional tinggi, migrasi berat, tidak cocok dengan Neon/Prisma multi-tenant sederhana.

**Konsekuensi**

**Positif:**
- Isolasi tenant ditegakkan di DB, bukan hanya konvensi kode.
- Query scope lebih sederhana (`unitId = ...`) dibanding rantai relasi panjang.
- Audit/forensik lebih jelas dengan `app.user_id`/`app.unit_id`.

**Negatif / Risiko:**
- Semua query tenant-scoped wajib dalam transaksi + `SET LOCAL`; disiplin tinggi.
- Backfill `unitId` pada data existing perlu skrip hati-hati.
- Policy RLS salah bisa memblokir data sah atau (jika salah arah) bocor; butuh test isolasi P1.
- Neon pooler harus transaction mode; `SET` session-level dilarang.

**Dampak ke Modul Lain:**

- `prisma/schema.prisma`: `directUrl`, `parentId`, `unitId` pada aggregate root, index.
- `lib/prisma.ts`: singleton + tenant-aware client extension / `withTenant` helper.
- `lib/api/auth.ts`: `AuthzSubject` membawa `unitId/scope`.
- Semua repository tenant-scoped: wajib lewat `withTenant`.
- `docs/backend/04.SECURITY.md`, `06.RBAC.md`: tambah kebijakan RLS.

## 6. Larangan Keras

- ❌ DILARANG membuat keputusan arsitektur penting tanpa mendokumentasikannya di ADR.
- ❌ DILARANG mengubah keputusan yang sudah Accepted tanpa membuat ADR baru.
- ❌ DILARANG menghapus ADR yang sudah ada (gunakan status Deprecated atau Superseded).
- ❌ DILARANG membuat ADR tanpa menyertakan alternatif yang dipertimbangkan.
- ❌ DILARANG implementasi keputusan sebelum ADR di-review dan di-Accept.
